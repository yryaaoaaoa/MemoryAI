# 错题本与掌握度修复验证

检查范围：刷题提交、答题记录、本轮重做、错题本接口、用户画像统计、掌握度读写及数据库升级。当前没有独立错题本或掌握度详情前端页面，本次没有新增页面。

## 修复

- 错题本按用户每题的最新记录计算，先筛选再分页；列表、数量、知识点统计及随机重做使用相同条件。
- 手动移除状态存入 `quiz_record.wrong_removed`，保留历史；再次答错重新进入错题本，答对自动移出。旧 Redis 状态已备份迁移。
- 提交答案与更新掌握度使用同一数据库事务；写入失败不会留下半条业务结果。
- 面试掌握度 upsert 在更新计数前计算比例，避免本次结果重复参与计算。
- 掌握度先衰减再排序，薄弱知识点选择与实际分数一致；历史最长连续正确从答题历史计算，后续答错不会抹掉纪录。
- 记录日期上限排除次日零点，同一秒的记录按 ID 稳定排序；记录筛选列出全部已答知识点。
- 前端提交每题实际用时，重做时重新计时；加载失败可以重试，筛选旧响应不会覆盖新结果。画像“待复习”改为对应接口含义的“错题数”。

## 验证证据

修复前临时账号某知识点只有 1 道当前错题，筛选接口却返回 `total=2`、空列表；旧知识点统计也计入已答对、已移除题。

修复后用两个隔离临时账号调用实际前端代理和后端接口，验证筛选分页、统计、手动移除、重新答错、答对移出、跨账号隔离、Redis 缓存清空后错题仍保留、全部知识点筛选、未作答交卷、非法参数、日期边界及答题用时。

人为让临时账号掌握度更新发生 SQL 溢出，确认接口失败后答题记录和错题数均未增加。面试掌握度验证直接执行服务中的 SQL，没有调用面试模型：先 4 次全错，再 2 次全对，最终正确 2/6、掌握度 33，而非重复计算的 50。

验证包含 Maven 后端测试、前端类型检查和生产构建、16 项 Playwright 浏览器回归。浏览器回归使用模拟接口；上述数据一致性验证使用真实 MySQL/Redis/API，无模型调用。
